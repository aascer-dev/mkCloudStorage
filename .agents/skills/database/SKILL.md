# MKCS MySQL 与 MyBatis-Plus

## 适用范围

处理表、字段、SQL、索引、迁移、Mapper 查询契约和持久化一致性。Redis 短期状态见 `redis`；事务代理见 `spring`；连接密钥见 `configuration`。

## 项目事实

- MySQL 使用 InnoDB 与 `utf8mb4`，Java 侧通过 MyBatis-Plus Mapper 和 `mkcs-server/src/main/resources/mapper/*.xml` 访问。
- 主键策略是 MyBatis-Plus `IdType.ASSIGN_ID`，全局配置在 `application.yml`。新实体和建表 SQL 不得改成 `AUTO_INCREMENT`，除非先完成独立的全项目迁移决策。
- Java 使用驼峰，数据库使用 `snake_case`；实体、XML、Mapper 方法和查询结果必须同步。
- 现有逻辑删除配置为 `deleted`。新增或修改逻辑删除前先检查对应实体与真实表，不能混用 `deleted`、`is_deleted` 和时间戳语义。
- 文件元数据、逻辑桶、ACL、分享、上传任务和内容索引属于 MySQL；实际对象和临时分片不写入数据库 BLOB。

## Schema 与 SQL

- 修改前检查实体、Mapper 接口、XML、调用 Service、现有 SQL 和迁移目录。不要凭名称猜测字段或表结构。
- 表和列使用有业务含义的 `snake_case` 名称；主键为 `BIGINT id`，关联列为 `*_id`。为用户、内容哈希、上传任务和权限等业务不变量设置唯一约束。
- 按真实 `WHERE`、`JOIN`、排序和唯一性设计索引；联合索引按查询前缀设计，避免重复和预防性索引。
- SQL 使用 `#{}` 参数绑定；动态列、排序字段和表名只能来自代码白名单。默认显式列出 SELECT 字段，分页必须有稳定排序。
- 内容去重、分片完成和引用计数的并发更新必须在事务内设计原子条件或受影响行校验，不能依赖“先查再写”。

```sql
-- Good: IDs are generated by MyBatis-Plus and duplicate chunks are impossible.
CREATE TABLE upload_task_chunks (
    id BIGINT NOT NULL,
    task_id BIGINT NOT NULL,
    chunk_index INT NOT NULL,
    status TINYINT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_upload_task_chunks_task_index (task_id, chunk_index),
    KEY idx_upload_task_chunks_task_status (task_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- Bad: AUTO_INCREMENT conflicts with IdType.ASSIGN_ID and lacks an invariant.
-- CREATE TABLE upload_task_chunks (id BIGINT AUTO_INCREMENT PRIMARY KEY, task_id BIGINT);
```

```xml
<!-- Good: bound parameters and stable ordering. -->
<select id="selectActiveByOwner" resultType="cn.zjj.mkcsmodel.entity.Files">
    SELECT id, bucket_id, owner_id, content_id, filename, parent_id, size, status
    FROM files
    WHERE owner_id = #{ownerId} AND status = 1
    ORDER BY updated_at DESC, id DESC
</select>

<!-- Bad: external input becomes executable SQL. -->
<!-- WHERE owner_id = ${ownerId} -->
```

## Mapper 与事务

- Controller 不直接使用 Mapper。Mapper 只访问数据，权限判断、对象存储调用和流程编排留在 Service。
- 多表写入、内容引用计数与文件状态切换的原子边界放在 Service 的 `@Transactional` 方法中。事务内不执行长时间上传、下载、邮件或远程对象操作；需要补偿时显式定义失败路径。
- XML 的 parameter/result 映射、实体字段和 Service 返回语义必须一致。修改查询后补覆盖空结果、重复键、分页和并发路径的测试。

## 迁移策略

根目录 `sql/` 是唯一数据库脚本来源。项目当前未引入 Flyway/Liquibase，不能假定应用会自动执行任何脚本；执行前必须确认脚本与目标库表结构匹配。`mkcs-server/src/main/resources/db/migration/` 不再保留迁移脚本，也不能作为执行入口。

- 先确认目标环境已导入的 `sql/` 脚本和表结构，并在部署记录中保存执行时间、操作者与校验结果。新增迁移脚本必须继续放在根目录 `sql/`，不得重新引入第二个迁移目录。
- 新增迁移优先使用不可变、递增的 `VYYYYMMDD_NNN__Description.sql` 命名；不要修改已在环境中执行过的脚本。
- 每个迁移应尽量可重复检查或明确前置版本，包含必要索引/数据回填，并说明回滚或恢复方式。破坏性变更先做兼容发布、回填和验证，未经授权不删除数据或列。
- 迁移后核对实体、XML、初始化数据与空库启动路径；实际执行的数据库验证必须如实记录。

```sql
-- sql/V20260916_001__add_file_index.sql
ALTER TABLE files ADD INDEX idx_files_owner_status (owner_id, status);
-- Include the precondition, backup and verification in the deployment record.
```
